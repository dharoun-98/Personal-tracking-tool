**Released:** 2026-08-10

## What this release is

Three promises from the original brief, made real: a light mode, the two
keepsake documents, and getting them to the player by email. Plus the settings
screen that Stage 1 stubbed out.

The accessibility work was not planned and turned out to be the largest part
of it. Building a light theme forced a real contrast audit, and that audit
found that **the dark theme had been failing WCAG AA since Stage 1**.

## Architecture decisions worth remembering

### Two token families, not one

The naive approach — one colour per domain — breaks immediately in light mode.
`#F5B301` is a lovely gold fill and an illegible text colour on white (1.85:1).

So every domain has two values:

- `color` — the fill. **Identical in both themes.** Orbs, bars, dots, washes.
- `ink` — a `var()` reference that flips per theme. Anything that sets *text*
  or a small icon in the domain's colour.

Plus `--color-on-accent`: near-black in **both** themes, for text sitting on a
saturated fill. It's theme-invariant on purpose — the fills don't change, so
the text on them shouldn't either, and a single invariant token can't desync.

`@theme inline` maps Tailwind's names onto `--c-*` variables, so `bg-surface`
has a runtime hook and there is not a single `dark:` utility in the codebase.

### Glow is a night-time device

`--c-glow-strength` is `1` in Night and `0.35` in Day; `--c-star-opacity` is
`1` and `0`. Every glow multiplies through it. On a pale background a coloured
bloom reads as a smudge, so Day earns depth from shadow and border weight
instead. The star field switches itself off rather than being a second
component.

### Transitions and theme changes don't mix

Two separate bugs, same root cause, both user-visible:

1. `body` had `transition: background-color, color`. On load, with the theme
   already applied by the boot script, Chrome started a transition anyway and
   left both properties **pinned at the dark values indefinitely** — light
   theme, dark background, unreadable.
2. Any element with `transition-colors` could pin the same way when the theme
   changed underneath it.

Fix: `applyToDocument` stamps `data-theme-switching` on `<html>`, which
disables every transition, then releases it on the next animation frame. Theme
changes are instant, which is the correct behaviour regardless.

### PDFs are built on the device

The server has no copy of anyone's history — that's the whole point of
local-first. So `@react-pdf/renderer` runs in the browser and the *client*
uploads the finished PDFs to the send endpoint.

The engine is ~1MB, so everything in `src/lib/pdf/` is behind a dynamic
`import()` and never enters the main bundle. Documents are regenerated on every
download rather than cached, so they always reflect the current profile.

The two documents are always light, regardless of app theme. They're keepsakes:
printed, emailed, opened years later. A dark-mode PDF is wasted toner.

### Baselines are immutable

Everything in `PlayerProfile` is editable at `/settings` **except** baselines.
They are the substance of the starting report. A record of day one that you can
retroactively edit is not a record.

Changing `priorities` is allowed but warns: it recalculates `balancedDays` in
`analysis.ts`, which moves progress on the "In Balance" achievement. Already
unlocked achievements are never revoked.

## The contrast audit

Written as a script run in-page against every route in both themes. It:

- resolves any CSS colour — including `oklab()` and `color-mix()` — to sRGB by
  painting it to a 1×1 canvas and reading the pixel back;
- composites the full ancestor background stack with real alpha, rather than
  assuming the nearest non-transparent parent is opaque;
- skips genuinely hidden elements via `getClientRects()`, and skips
  gradient-painted text (`background-clip: text`), whose computed `color` is
  `transparent` and therefore meaningless.

The first two versions of that script produced mostly phantoms — `oklab()`
parsed as RGB, and `display:none` subtrees counted. **Worth remembering: an
accessibility checker that hasn't been checked is a generator of confident
nonsense.**

Result: 10 routes × 2 themes, **0 failures**.

Fixes it forced:

| --- | --- | --- | --- |
| `--c-ink-mute` (Night) | `#7d79ab` | 4.14:1 on surface-3 | `#a9a5d4` |
| `--c-ink-faint` (Night) | `#55527d` | **2.30:1** on surface-2 | `#8c88bc` |
| `--c-success` (Day) | `#0f9e78` | 2.98:1 on surface-2 | `#0a7256` |
| `--c-warn` (Day) | `#a06f02` | 3.74:1 | `#8a5b00` |

| `--c-violet-soft` (Day) | `#6d5ef6` | 4.23:1 | `#6151e4` |
| `.gold-sheen` mid stop (Day) | `--c-gold` | **1.85:1**, no fallback | `--c-sheen-b` |

## Verified before release

- `tsc --noEmit` clean, `eslint` clean, production build succeeds — 13 routes.
- Both documents render, including the "skipped every optional question"
  variant, via `docs/tooling/render-sample-pdfs.tsx`.
- Document text content asserted by inflating the PDF streams and decoding the
  hex-encoded `TJ` operators — headings, ordering, page numbering and the
  12-month look-back date all confirmed.
- Send endpoint returns `{configured:false}` and a 503 with a readable message
  when no provider is set; the UI hides the card rather than offering a button
  that can only fail.
- 20 route/theme contrast checks, zero failures.
