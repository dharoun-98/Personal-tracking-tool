# v0.3.0 — Stage 3: Accounts, billing and the command deck

**Released:** 2026-08-10
**Tag:** `v0.3.0`

---

## What this release is

The business layer. Accounts, cloud backup, a trial that actually ends, a
paywall, an admin panel, and Stripe.

The constraint that shaped all of it: **the game must still run with none of
this configured.** Someone cloning this repo, running `npm run dev` and
opening localhost gets a complete, playable app with no backend, no keys and
no signup. Every capability below is additive and degrades to a readable
"not switched on" message rather than an error.

## Architecture decisions worth remembering

### Backup, not sync — and it asks before overwriting

`src/lib/sync/sync.ts` pushes the device's whole state and mirrors it, rather
than merging. Real multi-device sync needs tombstones for every deletion,
per-field timestamps or vector clocks, and a conflict policy per entity. Get
any of it subtly wrong and you lose somebody's 90-day streak silently, months
later.

So when the device and the cloud both hold a game, the player is shown what's
in each and asked which to keep. "We chose the newer one" is not a defence
when the newer one was a fresh install.

### `accounts` is read-only to the player

The single most important line in the schema:

```sql
create policy "own account read" on public.accounts for select using (auth.uid() = id);
```

Select only. No insert, no update. Every field that decides whether someone has
paid — `status`, `bypass_billing`, `trial_days`, `current_period_end` — is
writable exclusively by the service role, which lives in the Stripe webhook and
the admin panel. A player can read their own billing state and change none of
it.

### Access is decided on the server

`(game)/layout.tsx` is a server component whose only job is to answer "is this
person allowed to play", from the account row. It passes the verdict to the
client shell. The browser's opinion of whether someone has paid is not
evidence.

Signed-out players fall back to the local trial clock, which *is* client-side
and therefore defeatable by clearing site data. That's inherent to a trial in
an app that works offline; the server check takes over the moment someone
signs in, which is where the money is.

### The webhook is the only thing that can grant access

`verifyWebhookSignature` is a constant-time HMAC check with a timestamp
tolerance, and the route refuses everything when `STRIPE_WEBHOOK_SECRET` is
missing. Without that check, anyone who discovered the URL could POST a
fabricated `checkout.session.completed` and hand themselves a subscription.

The raw request body is used for verification — parsing and re-serialising
changes the bytes and the signature never matches.

### Admin is deliberately not Supabase auth

A shared password and an HMAC-signed cookie, exactly the WordPress model that
was asked for. The reason to keep it separate: the admin needs to get in
precisely when the app's auth is what's broken.

Every mutating server action re-checks the session itself. Server actions
compile to POST endpoints with stable ids — a check in the page protects the
render, not the action.

### No Stripe SDK

Three endpoints don't justify shipping the `stripe` package to everyone who
just wants to play. Two `fetch` calls and a `createHmac` do the same job.
`toFormBody` handles Stripe's nested form encoding (`a[b][0][c]`).

### The paywall shows their real numbers

Level, streak and XP, read from local state, on the lock screen. The data
isn't gone — it's sitting right there on the device — and the screen says so
and proves it. A paywall that feels like a hostage situation earns a
chargeback, not a subscription.

## Things that fought back

**The hand-written `Database` generic didn't work.** Every query resolved to
`never`. The exact shape supabase-js expects moves across minor versions, and
the installed `postgrest-js` in this tree is a stub, so it couldn't be read
from source either. Dropped the generic entirely — the client is untyped and
every row crosses into application types through an explicit mapper in
`src/lib/sync/mapping.ts`, which is where the checking that matters happens.

**`Date.now()` in a server component** trips the React Compiler purity rule.
The admin dashboard now evaluates access client-side against the shared clock,
which is better anyway: "3 days left" keeps ticking on a dashboard left open.

## Verified before release

- `tsc --noEmit` clean, `eslint` clean, production build succeeds — 22 routes.
- Every page renders 200 with **no** Supabase configured: dashboard, account,
  profile, both auth pages, and the command deck.
- All three service routes return 503 with a readable message when unconfigured
  (`/api/billing/checkout`, `/api/billing/portal`, `/api/documents/send`).
- Trial lifecycle exercised end to end against the local clock:
  day 3 → silent, full board; day 13 → gentle banner, full board; day 20 →
  paywall replaces the app and the board is gone.

**Not verified:** anything requiring live Supabase or Stripe credentials. The
migration has not been run against a real database, no account has actually
been created, and no payment has been taken. Those need the keys.
